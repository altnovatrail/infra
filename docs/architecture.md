# infra — архитектура

> Статус: каркас из заготовки `spec`, 2026-10-19.
>
> Что делает компонент, чего не делает и что о нём ещё предстоит решить. Это подробности его карточки — architecture 3.11 spec. Карточка остаётся сводкой: если подробности меняют то, что в ней сказано, она правится в `spec` тем же путём, что и вопросы в его реестры (RULES.md, Across repositories).
>
> Почему решено так, а не иначе, — в [decisions.md](decisions.md); план работ — в [RUN.md](../RUN.md). Понятия — concepts spec. Документы и решения `spec` лежат в `spec/docs/` и цитируются с суффиксом «spec».

## 1. Назначение и границы

**Делает:**
- описывает кодом общую основу платформы: проекты в облаке, Workload Identity Federation для CI, Artifact Registry, домены, Secret Manager и бюджеты (architecture 3.11 spec). Основа — технологическая база MathTrail Canvas: Cloud Run и управляемые сервисы с масштабированием до нуля, Terraform (R11 spec). Образец — `infra/` canvas-api: `bootstrap.sh` и один корневой модуль Terraform. Будет ли это Terraform или его открытый форк OpenTofu, решит первый код `infra` (architecture 3.11 spec; Т-29);
- настраивает журналы и трассы платформы — Cloud Logging и Trace (architecture 3.12 spec):
  - журналы запросов Cloud Run исключаются в Cloud Logging. Cloud Run пишет их сам, и в их поле `httpRequest` есть IP-адрес клиента, а COPPA относит IP-адрес к персональной информации (architecture 1 spec; privacy 4 spec);
  - регион журналов — `us-east4`, а бакет `_Required` — в `global`, пока нет организации Google Cloud (R04; R109 spec);
- выбирает и настраивает хостинг сборки `app` (Т-17), а к этапу 4 — домен виджетов, отдельный регистрируемый (R16 spec), и хостинг виджетов (architecture 3.12 spec; Т-17). Платформе годится только хостинг, который шлёт свои заголовки ответа — CSP по `csp.json` сборки и кеш, — и отдаёт `/deployment.json` вне архива сборки (Т-17; architecture 3.12 spec). На хостинг сборки `app` потом переезжает и страница образцов `canvas` (R25 spec);
- выкатывает сервисы и сборку `app` по одному списку точных версий и дайджестов — это решил R106 spec, и Т-19 закрыт. На схеме зависимостей `infra` выкатывает релизы `api` и `app` (repositories 3 spec). Как идёт выкладка (R105 spec, R106 spec; architecture 3.11 spec):
  - образ сервиса собирает выкладка `infra`: берёт из релиза сервиса бинарник и `Dockerfile`, проверяет их рецептом `spec` `release-verify` (R77 spec), собирает образ на базе `gcr.io/distroless/static-debian13:nonroot` по digest, кладёт его в закрытый Artifact Registry `infra` и выкатывает ревизию Cloud Run по digest образа. Что сервис кладёт в образ сверх бинарника, делает его собственный код на стадии сборки: у `api` это пакеты модулей. Образов NovaTrail не публикует (RULES.md, Production images);
  - сборку `app` выкатка проверяет по подписи архива, пишет `/deployment.json` из списка выкатки, проверив его по `deployment.schema.json` этой сборки, собирает заголовок CSP по её `csp.json` и выпускает сборку, файл и заголовок одним выпуском хостинга (R85 spec). Список называет рядом с дайджестом сборки дайджест её `/deployment.json` (Т-19);
  - откат — revert списка. `api`, а пока формат модуля v0 — и сборка `app`, перешедшая на новую версию формата, откатываются только вперёд (Т-19);
  - задания `api` при выкладке — миграции до приёма запросов, задание после выкладки — когда ревизия приняла весь трафик — выкладка запускает тем же образом, а факты развёртывания и нижнюю ступень допуска `api` передаёт ревизии из своего репозитория (поправка 2026-11-08 к R106 spec);
  - что остаётся здесь: формат и место списка и кто его правит, что выкатка проверяет до выкладки, отклонять ли релиз `api` ниже выкаченного и как ревизия `api` получает факты и ступень — раздел 2.2;
- даёт self-hosting и локальный запуск всей платформы (architecture 3.11 spec): код открыт, и свою копию платформы оператор может развернуть сам (product 3 spec). Self-hosting берёт тот же список и тот же путь выкладки: собирает образ у себя из того же бинарника и по тому же `Dockerfile` (R105 spec, R106 spec). Подписанная сборка `app` у всех одна: конфигурацию развёртывания она читает во время работы из `/deployment.json`, а его оператор self-hosting пишет сам по той же схеме (R85 spec; Т-19). Свои факты для допуска к ИИ self-hosting заявляет сам (Т-20; R96 spec).

**Не делает:**
- не хранит данных учеников: из частей платформы их на сервере хранит только `api` (architecture 1 spec; R15 spec). Базу и сервис входа выбрал `api`: Neon Postgres и Firebase Auth (architecture 3.12 spec);
- не держит секретов в репозитории: ключи поставщиков ИИ лежат в Secret Manager (architecture 3.12 spec), а читает их сервисный аккаунт `api` (R15 spec). Если Т-28 решится по рекомендации, там же ляжет и отдельный ключ платформы для eval (R24 spec), и читать его будет CI `modules` и `tutor` через Workload Identity Federation. Значения ключей — никогда не в файлах репозитория (RULES.md, Hard rules);
- не держит кода сервисов и не выпускает их релизы: релиз с подписью — общий workflow из `.github`, который берёт каждый репозиторий с кодом (architecture 3.11 spec; repositories 2.1 spec);
- не заводит своих кластеров, очередей и шины событий. Фоновые работы — задания Cloud Run по расписанию (architecture 1 spec; R11 spec); Cloud Scheduler и задания Cloud Run выбирают `api` и `infra` вместе (architecture 3.12 spec);
- не раздаёт пакеты модулей в первом срезе: на этапе 2 они лежат в образе `api`, и медиафайлы раздаёт `api` (architecture 3.10 spec). Кладёт их в образ код самого `api` на стадии сборки, и логики пакетов выкладка не повторяет (R106 spec). Хранилище с CDN в `infra` по рекомендации Т-17 появится, когда модулей станет больше или придут сторонние авторы (repositories 8 spec);
- не решает регион данных один: его решил `spec` — США, одно место на всех учеников (R109 spec; П-11 закрыт), — а здесь только то, что из этого следует для ресурсов `infra` (R04).

**Данные и связи:**
- данных учеников и секретов в репозитории нет, как ни в одном (RULES.md, Hard rules). Но то, что он настраивает, — журналы, регион, хостинг — касается данных учеников, поэтому каждое предложение здесь сначала читается по privacy spec (RULES.md, Hard rules). Хостинг и инфраструктура — обработчики данных (privacy 2 spec);
- в журналах — события, коды, время и версии, без прямых идентификаторов, IP-адресов, работ, прочитанного и текста подсказок (R09 spec; privacy 4 spec; architecture 5 spec). Сроки хранения — П-9;
- хостинг `app` и сервис входа пишут IP-адрес в свои журналы сами. Эти журналы решаются вместе с выбором этих сервисов: хостинга — здесь, сервиса входа — в `api` (architecture 1 spec; architecture 3.12 spec; privacy 4 spec; П-9). Сервис входа `api` выбрал — Firebase Auth: IP-адреса он держит несколько недель, а получает их не только при входе — на iPad, в Safari и в мобильных браузерах его скрипт и iframe грузятся при каждом старте `app` (privacy 4 spec; architecture 3.12 spec; П-9);
- при сборке ни от чего не зависит, кроме `spec`, и по сети ни к кому не обращается (repositories 2.1 spec). На схеме зависимостей его стрелки — выкладка релизов `api` и `app` (repositories 3 spec);
- общие проверки CI — поиск секретов, DCO, CodeQL, Scorecard и проверку документов — берёт из `.github` ещё до кода; подключила их T21 `spec` (R30 spec; architecture 3.11 spec);
- файл релиза NovaTrail — бинарник сервиса, его `Dockerfile`, архив сборки `app` — входит в выкладку, только когда его принял рецепт `spec` `release-verify` (RULES.md, Release files are verified; R77 spec). Т-27, что сверяет эта проверка, закрыт им же;
- его сервисы (architecture 3.12 spec): хостинг сборки `app`, домен и хостинг виджетов на этапе 4, Secret Manager, Artifact Registry, Cloud Logging и Trace, а вместе с `api` — Cloud Scheduler и задания Cloud Run;
- этап 2, вместе с `tutor`, `canvas`, `api`, `app` и `skill-map` (product 11 spec). Репозиторий заведён раньше кода ради документов, а код ждал П-11 — регион данных, который нужен до первого развёртывания (architecture 3.11 spec; repositories 2.1, 6 spec). П-11 закрыт решением R109 spec (R03). Первое приложение — у автора, локально и без развёртывания, так что строку `infra` в сквозном плане `spec` автор отложил до первого развёртывания (R76 spec). Terraform или OpenTofu встанет в devcontainer вместе с кодом (T14 `spec`), а который из них — Т-29: он вырос из вопроса В2 этого репозитория, и решает его первый код `infra`.

## 2. Решить при детализации

Пункты «Решить при детализации» из карточки — по подразделу на пункт, а два пункта о выкатке — в одном, 2.2. Каждый решает своя задача эпика E1 в [RUN.md](../RUN.md). Решённый пункт называет запись журнала, а само решение переезжает в раздел 3. Вопрос, который выходит за этот репозиторий, уходит «в реестр spec» (RULES.md, Across repositories).

Регион карточка больше не спрашивает: П-11 закрыт решением R109 spec, а подраздел 2.1 решён (R04). У карточки на v0.9.13 четыре пункта — список версий и проверки выкатки и то, как ревизия `api` получает факты развёртывания и ступень допуска, — оба в подразделе 2.2, — хостинг и домены — 2.3 — и Terraform или OpenTofu — 2.5. Хостинг с доменами связан с открытым вопросом реестра `spec` Т-17, а домены ещё и с О-16. Решение, которое закрывает такой вопрос, записывается в `spec` (RULES.md, Across repositories). Поэтому задача здесь готовит варианты и рекомендацию и передаёт их «в реестр spec», а в журнал этого репозитория идёт то, что из решения следует для `infra`. Хостинг сборки `app` Т-17 тоже называет, но выбирает его `infra` (architecture 3.12 spec): Т-17 оставляет выбор T03 — по тому, что хостинг пишет в журналы. Кто выкатывает, решил R106 spec и закрыл Т-19, так что пункт 2.2 — уже только об устройстве списка, проверках выкатки и о том, как ревизия `api` получает факты развёртывания и ступень допуска, и решается он здесь. Terraform или OpenTofu — Т-29, и решает его первый код `infra`.

Подраздел 2.4 — сверх списка карточки. Карточка называет исключение журналов запросов среди того, что `infra` делает, а architecture 1 spec — среди принципов. Но среди пунктов «Решить при детализации» его нет, хотя как исключать, сказано только в общих словах: «журналы запросов исключаются в Cloud Logging». Пункт называет задача, которая завела этот репозиторий (T14 `spec`), и решить его нужно до первого развёртывания: регион журналов уже решён (R04; architecture 1 spec). Карточку под него правит итог детализации, T05, — строкой таблицы 3 «в реестр spec», когда решение принято, а не заранее (начало architecture 3 spec).

### 2.1. Регион (П-11)

- **Решено:** R04, по R109 spec — П-11 закрыт: США, одно место на всех учеников, всё, что `infra` держит в регионе, — `us-east4`, а Neon `api` — `aws-us-east-1`. Регион каждого ресурса — раздел 3.1. Рекомендацию готовила T01 строкой В3 таблицы 3 [RUN.md](../RUN.md), «в реестр spec», а записала T08, переходом на `spec` v0.9.13 (R03).
- **Задача:** T01, T08.

### 2.2. Список версий и проверки выкатки (R106 spec)

- **Суть:** где лежит список выкатки, что он называет, кто его правит, что выкатка проверяет до выкладки и как идёт откат. Это пункт карточки (architecture 3.11 spec). Кто выкатывает, решил R106 spec — `infra`, по одному списку точных версий и дайджестов, и сервисов, и сборки `app`, — и Т-19 закрыт. Остальное R106 spec оставил этому репозиторию: формат и место списка и кто его правит, что выкатка проверяет до выкладки и отклонять ли релиз `api` ниже выкаченного. Поправка 2026-11-08 к R106 spec добавила пункт карточки — как ревизия `api` получает факты развёртывания и нижнюю ступень допуска, которые `infra` держит рядом со списком.
- **Что известно:**
  - путь выкладки задан R105 spec и R106 spec: образ сервиса собирает выкладка `infra` из бинарника и `Dockerfile` его релиза, на базе по digest, кладёт в закрытый Artifact Registry и выкатывает ревизию Cloud Run по digest образа; сборку `app` — проверка подписи архива, `/deployment.json` по `deployment.schema.json` сборки и CSP по её `csp.json`, одним выпуском хостинга (раздел 1). Self-hosting идёт тем же путём в своём проекте;
  - откат — revert списка, а `api` откатывается только вперёд: revert вернул бы образ `api` со старым релизом `modules`, где снятая с тех пор версия снова стала бы текущей. Пока формат модуля v0, только вперёд откатывается и сборка `app`, перешедшая на новую версию формата (Т-19);
  - на схеме зависимостей `infra` выкатывает релизы `api` и `app` (repositories 3 spec). Workload Identity Federation для CI — тоже `infra`, и репозиторий компонента доступа к production не имеет (architecture 3.11 spec; R106 spec);
  - релиз с подписью — общий workflow `.github`, а подписи — без ключей, через Sigstore, как R52 canvas-api (architecture 3.11, 3.12 spec);
  - что сверяет подпись, решил R77 spec, и Т-27 закрыт: и SAN — путь общего `release.yml` `.github` с SHA коммита его релиза не ниже v0.1.7, который лежит на истории `main` `.github`, — и репозиторий и workflow вызывающего. Сверяет её один рецепт `spec`, `release-verify`; если Sigstore или GitHub не отвечают, файл отклоняется (architecture 3.12 spec). Правило и рецепт для выкатки — R77 spec, а что выкатка проверяет и чем сверх него, решает `infra` (Д54 в таблице 4 RUN.md `spec`);
  - пакеты модулей закрепляет конфигурация `api`, `modules.json`: тег релиза `modules` и дайджест его индекса, а дайджесты пакетов называет индекс (Т-17; architecture 3.10 spec). В образ их кладёт код `api` на стадии сборки (R106 spec), так что список выкатки называет релиз `api`, а не пакеты;
  - формат `/deployment.json` — пока R09 app, а его правила — схема и шаблон CSP в подписанной сборке `app`. В `spec` нормативной частью он переходит с первым развёртыванием, когда выкатка `infra` станет его вторым читателем в коде (R85 spec);
  - задания `api`, которые держатся за выкладку, запускает выкладка `infra`, заданиями Cloud Run тем же образом, что и ревизия: миграции обеих баз — до того, как ревизия примет запросы, а задание, которое закрывает попытки и прохождения на пакетах, ушедших из образа, — когда ревизия приняла весь трафик. Имена команд бинарника называет релиз `api` (поправка 2026-11-08 к R106 spec);
  - факты развёртывания для функции допуска к ИИ и нижнюю ступень правила допуска моделей `api` держит `infra`, рядом со списком выкатки, правкой своего pull request, а выкладка передаёт их ревизии `api` (R25 api; поправка 2026-11-08 к R106 spec). Как ревизия их получает, решает T02;
  - в canvas-api выкладка идёт после релиза, из его тега: `terraform apply` из коммита тега, затем образ и новая ревизия, затем сборка приложения. Выкладка идёт, только если `main` всё ещё стоит на коммите релиза (R45 canvas-api, R58 canvas-api; раздел 4 этого документа). Там это был один репозиторий, а в NovaTrail релизы выходят из разных (R10 spec).
- **Варианты:** пока пусто.
- **Задача:** T02.

### 2.3. Хостинг сборки `app` и домены (Т-17)

- **Суть:** где раздаётся сборка `app` и на каких доменах живут `app`, `api` и, к этапу 4, виджеты. Хостинг сборки `app` выбирает `infra` (architecture 3.12 spec), и Т-17, вопрос реестра `spec`, оставляет этот выбор здесь. Домен виджетов — отдельный регистрируемый (R16 spec), а регистрация основного домена ждёт проверки товарного знака (О-16).
- **Что известно:**
  - в canvas-api хостинг сборки — Firebase Hosting (architecture 3.12 spec);
  - хостинг `app` сам пишет IP-адрес в свои журналы, как записано по canvas-api. Эти журналы решаются вместе с выбором хостинга, а их сроки — П-9 (architecture 1 spec; privacy 4 spec). Хостинг — обработчик данных (privacy 2 spec);
  - `app` читает конфигурацию развёртывания во время работы, из `/deployment.json`, так что хостинг раздаёт одну подписанную сборку без пересборки под окружение (R85 spec; Т-19);
  - что хостинг сборки `app` должен уметь, решил автор по рекомендации `app` (Т-17): отдавать `/deployment.json` вне архива сборки; `index.html` и `/deployment.json` — с `Cache-Control: no-cache`, а `/assets/**` — immutable; держать файлы прошлого релиза и не отдавать `index.html` на запросы к ним и к `/deployment.json`; слать свои заголовки ответа — CSP по `csp.json` сборки с `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff` и HSTS — и не слать `Cross-Origin-Opener-Policy: same-origin`, который рвёт окно входа Firebase. Платформе годится только хостинг со своими заголовками, а self-hosting на хостинге без них `infra` описывает как более слабую защиту (Т-17; architecture 3.12 spec);
  - `app` живёт в корне своего origin, а `api` — на том же origin или на своём (Т-17). Каждое развёртывание ставит домен `app` в разрешённые домены своего проекта Firebase (Т-19; architecture 3.12 spec);
  - в canvas-api своего домена не было: API отвечал по адресу Cloud Run `*.run.app`, а приложение — по адресу Firebase Hosting `web.app`, и только этот адрес был разрешён в CORS API. Свой домен закрытой бете по приглашениям не нужен, а domain mapping Cloud Run был в Preview (R55 canvas-api; раздел 4 этого документа);
  - Т-17 — о том, где хранить и как раздавать пакеты модулей, медиафайлы и бандлы виджетов и где хостится сборка `app`. Рекомендация: на этапе 2 пакеты — в образе `api`, медиафайлы раздаёт `api`; хранилище с CDN в `infra` — когда модулей станет больше или придут сторонние авторы. Домен виджетов — отдельный регистрируемый, купить его вместе с основным после О-16. ### 2.4. Исключение журналов запросов

- **Суть:** как именно журналы запросов Cloud Run не попадают в хранилище журналов, какие ещё журналы платформы несут IP-адрес клиента и что остаётся для разбора сбоев, когда журналов запросов нет. Это сверх списка карточки (см. начало раздела).
- **Что известно:**
  - Cloud Run сам пишет журналы запросов со стандартным полем `httpRequest`, в нём `remoteIp` — IP-адрес клиента. Объём журналов запросов из Cloud Run не настраивается, но Cloud Logging умеет их исключать (architecture 1, 8 spec);
  - COPPA относит IP-адрес к постоянным идентификаторам, то есть к персональной информации (architecture 1 spec);
  - журналы платформы — без прямых идентификаторов, IP-адресов и содержания (R09 spec; privacy 4 spec). `api` сам не пишет их в журналы (architecture 3.5 spec);
  - фильтр исключения — часть sink: запись, которая подходит под фильтр исключения, этот sink не направляет никуда (раздел 4 этого документа). Значит, исключать надо в каждом sink, который мог бы направить такую запись;
  - применяется фильтр к записям, которые Logging API уже принял (раздел 4 этого документа): IP-адрес до Cloud Logging всё равно доходит, хотя и не хранится. Что это значит для обещаний privacy spec, решает задача;
  - в canvas-api журналы запросов не исключались: они лежали в бакете журналов 30 дней (R57 canvas-api), а вопрос о них в privacy.md canvas-api открыт, с рекомендацией сократить срок (раздел 4 этого документа);
  - Cloud Logging и Trace выбирает `infra`, и в них не должно быть прямых идентификаторов и IP-адресов (architecture 3.12 spec). Пишут ли IP-адрес трассы Cloud Run, не проверено — это выясняет задача;
  - сам хостинг `app` выбирается в подразделе 2.3, а сервис входа выбрал `api` — Firebase Auth (architecture 1, 3.12 spec). Но если их журналы попадут в Cloud Logging проекта, их направят те же sink, что настраивает `infra`: тогда исключать нужно и их. Сроки хранения — П-9: IP-адреса Firebase Auth держит несколько недель (privacy 4 spec);
  - в проекте будут и задания Cloud Run `api` — задание после выкладки и ежедневное задание оператора (architecture 3.12 spec). Их журналы пишет код самого `api`, а он IP-адресов в журналы не пишет (architecture 3.5 spec). Что Cloud Run пишет о заданиях сам, сверх их журналов, выясняет T04.
- **Варианты:** пока пусто.
- **Задача:** T04.

### 2.5. Terraform или OpenTofu (Т-29)

- **Суть:** чем `infra` описывает инфраструктуру. R11 spec называет базой Terraform, а Terraform с версии 1.6.0 вышел из открытых лицензий. Вопрос завёл этот репозиторий строкой В2 таблицы 3 [RUN.md](../RUN.md), а `spec` записал его в свой реестр как Т-29 и поставил в пункты карточки (architecture 3.11 spec).
- **Что известно:**
  - варианты Т-29 — Terraform по точной версии, названным исключением в решении `infra`, которое вводит его в devcontainer; OpenTofu по точной версии, тоже названным исключением, и поправка к R11 spec с правкой карточки 3.11 spec и мест, где назван Terraform; Terraform 1.5.7, последний под MPL 2.0 (repositories 8 spec);
  - рекомендация — предварительно OpenTofu, а решить в эпике первого кода `infra`, до того как инструмент встанет в devcontainer. MPL 2.0 проходит правило о лицензиях инструментов прямо, а грант BUSL — не об открытом коде, а о конкуренции, и его условия принимал бы и self-hosting (Т-29; раздел 4 этого документа);
  - поправка 2026-10-22 к R12 spec пускает и условия, бесплатные для всех, но только у инструмента, который NovaTrail не распространяет и без которого платформу можно собрать, запустить и развернуть. Terraform нужен, чтобы её развернуть, и рекомендация Т-29 прежняя (RULES.md, Hard rules; Т-29);
  - цена OpenTofu — правка мест, где назван Terraform, и проверка, что код по образцу canvas-api идёт под OpenTofu: здесь это не проверялось.
- **Варианты:** в Т-29.
- **Задача:** эпик первого кода; его предлагает T05.

## 3. Устройство

Сюда переезжает то, что решено по разделу 2: из каких частей компонент состоит, его типы и данные, как он связан с другими репозиториями. Пока решён только регион.

### 3.1. Регион

Регион платформы — США, одно место на всех учеников (R109 spec; П-11 закрыт). Что это значит для ресурсов `infra` — R04. Источники — раздел 4.

| Ресурс | Место | Почему так и что после создания не меняется |
|---|---|---|
| сервисы и задания Cloud Run | `us-east4` (Ashburn, Virginia) | рядом с Neon `aws-us-east-1` базы `api`; цены Tier 1 |
| репозиторий Artifact Registry | `us-east4`, регионально | место репозитория не меняется; мультирегион медленнее |
| секреты Secret Manager | репликация по выбору, место `us-east4` | места репликации не меняются; автоматическая репликация — без ограничений, а региональный секрет доступен только из своего региона, и CI на GitHub, который читал бы ключ eval по Т-28, его бы не прочитал |
| бакет журналов | свой, `us-east4`; sink `_Default` направлен в него | бакет `_Default` создан в `global`, и место бакета не меняется — меняется sink. Журналы запросов Cloud Run исключаются (раздел 2.4) |
| бакет `_Required` | `global` | sink `_Required` не меняется, а регион бакету даёт только настройка организации или папки до создания проекта; организация связана с доменом, которого до О-16 нет — Д3 в таблице 4 [RUN.md](../RUN.md) |
| бакет трасс `_Trace` | `us-east4`, создаётся через Observability API до первой трассы | иначе место выберут настройки по умолчанию или сама система, а сменить его может только reprovision, который трассы стирает |

Не `infra`: базу Neon `aws-us-east-1` держит `api`; Firebase Auth обрабатывает данные только в США при любом регионе; хостинг сборки `app` выбирает T03, а Firebase Hosting — глобальный сервис; регион вызовов ИИ R109 spec не решает (R96 spec).
