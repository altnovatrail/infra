Cloud Run даёт выбрать версию секрета, смонтированного томом: «You can select a specific version if you want», а по умолчанию берёт последнюю ([Configure secrets](https://docs.cloud.google.com/run/docs/configuring/services/secrets), обновлено 2026-10-30, прочитано 2026-11-08). Версия закреплена в ревизии, и откат ревизии её воспроизводит. Секретов в фактах нет (R25 api), а секрет здесь — только способ отдать ревизии файл: `spec` называет факты файлом конфигурации развёртывания `api`, его тип и чтение — у `tutor` ([текст таблицы допуска](../spec/admission/README.md), раздел 5; architecture 3.6 spec). `api` читает секреты из файла по пути в переменной `X_FILE` (R26 api) — так же он прочтёт и файл фактов. Имена переменных — строка В4 таблицы 3 RUN.md, «в реестр spec».
- **Откат.** `api` — только вперёд, новым релизом: тег ниже не пустят ни CI, ни выкладка (R106 spec; Т-19). Сборка `app` — pull request, который возвращает её блок списка к прежним значениям: revert целого коммита, который поднял и `api`, понизил бы `api` и был бы отклонён. Перешедшая на новую версию формата модуля сборка `app` — только вперёд, и это проверяет автор в ревью. Факты и ступень — pull request с прежними значениями: новая ревизия на том же образе. Срочно закрыть ИИ платформы — снять факт таким же pull request (R96 spec).
- **Self-hosting** держит такой же каталог `deploy/` со своими `deployment.json` и фактами и идёт тем же путём в своём проекте и своём реестре (R105, R106 spec; Т-20). Поэтому проверки и шаги выкладки — рецепты, которые запускаются и без GitHub Actions; их имена и workflow — первый код `infra`.

— *Почему:*
- JSON со схемой — как `modules.json` `api` и сам `/deployment.json`: разбор однозначен, а проверка схемой — та же, что у соседей;
- pull request руками — у общего `release.yml` `.github` v0.1.21 нет выходов, а у `api` и `app` ещё нет релизов: сцепить выкладку с релизом, как canvas-api, нечем, а каждый релиз и так проходит ревью автора;
- отказ релизу `api` ниже — и в CI, и в выкладке: CI показывает ошибку до мержа, а выкладка сверяет с тем, что выкачено на самом деле. Revert списка иначе вернул бы образ `api` со старым релизом `modules`, где снятая версия снова стала бы текущей (Т-19);
- файл фактов томом — так держится текст `spec`, который называет их файлом, а версия секрета закреплена в ревизии, как значение переменной. Ступень `spec` называет значением конфигурации (поправка 2026-11-08 к R76 spec), и ей хватает переменной;
- выкладка того, что изменилось, — снятие факта не должно ждать сборки, миграций и Sigstore, а откат `app` — пересборки `api`.

— *Отвергнуто:*
- YAML — у него неоднозначности разбора, а соседние файлы — JSON;
- переменные Terraform или OpenTofu — список стал бы зависеть от Т-29, а образ, задания и выпуск хостинга в Terraform не ложатся: canvas-api держал образ вне Terraform (раздел 4 [architecture.md](architecture.md));
- обязательное одобрение environment — второе одобрение того же автора сверх ревью pull request;
- pull request от релизов сервисов — CI `api` и `app` понадобился бы токен записи в `infra`. Добавить его можно потом, поверх этого пути;
- предупреждение вместо отказа и «не проверять» — revert списка тогда вслепую вернул бы снятую версию модуля;
- факты переменной окружения, JSON одной строкой, — первый ответ автора при планировании: `spec` называет факты файлом, а его тип и чтение — у `tutor`, и пришлось бы править нормативный текст `spec` (ревью T02);
- факты файлом в образе — «в образ и в git `api` они не входят» (R25 api), а смена факта ждала бы новой сборки;
- выкладывать всё на каждом мерже — снятие факта ждало бы Sigstore и миграций, а откат `app` пересобирал бы `api`.

## Хостинг и домены

**R06. Сборку `app` раздаёт Firebase Hosting — сайт проекта платформы по умолчанию. Своего домена у первого развёртывания нет: `app` живёт на адресе `web.app` проекта, а `api` — на своём адресе Cloud Run `*.run.app`, с CORS точному origin `app`. Когда покупать основной домен и домен виджетов, решает `spec` (О-16, Т-17); рекомендация `infra` — вместе после О-16, до публичного запуска (В6).** Ответы автора 2026-11-08 при планировании T03, все три — по рекомендациям. Т-17 оставил выбор хостинга сборки `app` этой задаче — по тому, что хостинг пишет в журналы (ответ на В13 `spec`; R01). Как он устроен — [architecture.md](architecture.md), раздел 3.3, а источники — раздел 4, прочитано 2026-11-08.
- **Хостинг** — Firebase Hosting, сайт проекта по умолчанию, план Blaze: на бесплатном Spark сайт при превышении квоты выключается, а оплата у проекта и так есть. Хранение до 10 ГБ и отдача до 10 ГБ в месяц — бесплатно. На Blaze потолка трат нет, так что бюджет проекта с оповещением ставит первый код `infra` (architecture 3.11 spec).
- **Выпуск сборки** — шаг выкладки `app` из R05. Выкатка собирает папку выпуска: архив новой сборки, `assets/` сборки, которая сейчас выпущена на Hosting, и `/deployment.json` из `deploy/production/deployment.json`. Затем пишет `firebase.json` и выпускает всё одной версией Hosting: «The content and configuration served by each channel is packaged into a version object».
  - **Прошлая сборка** — та, что сейчас выпущена, а не та, что названа в списке на `main`: `main` может опережать production, если прошлая выкладка не дошла (R05). Тег выпущенной сборки выкатка пишет в выпуск Hosting и читает оттуда; как — первый код. Её архив проходит те же проверки, что новый: `release-verify` и sha256 — в задание, которое достаёт production, попадает только проверенный файл (R05). У первого выпуска прошлой сборки нет, и папка — только новая сборка.
  - Файлы прошлой сборки выкатка кладёт сама: версия — полный набор файлов, а Т-17 велит держать файлы прошлого релиза. canvas-api этого не делал, и его следующий релиз убирал файлы прошлого.
  - `headers`: на всех путях — `X-Content-Type-Options: nosniff` и HSTS; на всех путях вне `/assets/**` — CSP по `csp.json` архива, с `{api}` и `{authDomain}` из `deployment.json` и с `frame-ancestors 'none'`, и `Cache-Control: no-cache`; у `/assets/**` — `immutable` (Т-17; architecture 3.7 app). Не по пути `index.html`: заголовки Hosting сверяет с путём запроса до rewrites, и путь SPA, который переписан на `index.html`, иначе остался бы без CSP и без `no-cache`;
  - rewrite SPA на `index.html` — только вне `/assets/**` и `/deployment.json`: Hosting переписывает путь, только если файла по нему нет, и без исключения отдал бы `index.html` на запрос к ушедшему файлу;
  - `Cross-Origin-Opener-Policy: same-origin` не шлётся: он рвёт окно входа Firebase (Т-17).

  После выпуска выкатка проверяет ответы: байты `index.html`, заголовки у `/`, у пути SPA и у файла в `/assets/`, `404` на неизвестный файл в `/assets/`, как `ci-hosting-check` canvas-api.
- **Откат** — по R05: pull request, который возвращает блок `app` списка. Откат версией в консоли Firebase не используется: правдой остаётся список.
- **Журналы.** Firebase Hosting сам хранит IP-адреса — «Hosting retains IP data for a few months», — и это не настраивается, а сервис глобальный: регион R04 его не держит. Выгрузку журналов Hosting в Cloud Logging не включать: она по выбору, и в её записях — `remoteIp`. Срок Firebase — строка В7 таблицы 3 RUN.md, «в реестр spec», к П-9 и privacy 4 spec. Хостинг — обработчик данных (privacy 2 spec).
- **Адреса:**
  - у первого развёртывания своего домена нет: `app` — `<проект>.web.app`, `api` — `*.run.app`. Так было и у canvas-api: «свой домен не нужен закрытой бете по приглашениям, а domain mapping Cloud Run в Preview» (R55 canvas-api);
  - сайт по умолчанию отвечает на двух адресах, `web.app` и `firebaseapp.com`, с одним содержимым. Origin `app` — только `web.app`: его называет CORS `api` и `/deployment.json`, а `app` с `firebaseapp.com` до `api` не дойдёт. `firebaseapp.com` проекта — `authDomain` Firebase Auth: `app` входит окном, страница входа — `/__/auth/handler` на нём, и на `web.app` её держать не нужно (R09 app);
  - выкатка добавляет `<проект>.web.app` в разрешённые домены проекта Firebase (Т-19) и не убирает домены, которые там ставит сам Firebase;
  - когда появится свой домен, его получает Hosting, а как его получит `api`, решается тогда же: domain mapping Cloud Run — в Preview. К домену виджетов этапа 4 `infra` сейчас ничего не готовит: где хостятся бандлы виджетов — Т-17.
- **Страница образцов `canvas`** переедет на Firebase Hosting, когда переедет (R25 spec), — отдельным сайтом проекта и своим origin: выход `app` стирает всё хранилище своего origin (architecture 3.7 app), а Hosting держит несколько сайтов в одном проекте. Ею делают и образцы детей (R25 spec), так что тогда IP-адреса и тех устройств, на которых их делают, попадут в журналы Firebase на тот же срок — это в В7.
- **Self-hosting** — любой хостинг, который шлёт свои заголовки, по тем же шагам; без своих заголовков — более слабая защита (Т-17).
- **Не проверено — первый код.** Умеют ли rewrites Hosting исключить `/assets/**` и `/deployment.json`: документация ссылается на синтаксис glob и RE2, а у RE2 нет lookahead. Если не умеют — rewrites называют пути SPA явно. И шлёт ли Hosting сам HSTS или `Cross-Origin-Opener-Policy`: проверка после выпуска сверяет заголовки ответа.

— *Почему:*
- из вариантов, которые шлют свои заголовки и выпускают файлы с заголовками одной версией, Firebase Hosting один не требует ни своего кода, ни своего домена, и он уже в том же проекте, что Firebase Auth;
- свой домен закрытому срезу не нужен, а О-16 велит проверить товарный знак до регистрации домена (product 13 spec);
- разные origin — запросы `api` не идут через хостинг, и его журналы не видят каждого запроса ученика; `api` CORS уже описал (architecture 3.9 api).

— *Отвергнуто:*
- Cloud Storage с внешним балансировщиком и Cloud CDN — у backend bucket журнал балансировщика «is automatically enabled and cannot be disabled», сертификату нужен свой домен, а выпуска одной версией нет;
- Cloud Run с сервером статики — это сервис со своим кодом и релизом (R105 spec), а кода сервисов в `infra` нет (CLAUDE.md, The component). Для статики Google называет Firebase Hosting и Cloud Storage;
- Cloudflare Pages — ещё один обработчик вне Google, срока хранения IP-адресов в его условиях не нашлось, а без `404.html` он отдаёт `index.html` на любой путь;
- GitHub Pages — своих заголовков не шлёт: «We don't support this feature today so a `meta` tag unfortunately is the only way» (сотрудник GitHub), а такой хостинг Т-17 отверг;
- свой домен у первого развёртывания — против О-16;
- один origin через rewrite Hosting в Cloud Run — каждый запрос к `api` попал бы в журналы хостинга, тайм-аут Hosting — 60 секунд, а буферизует ли он ответы, не проверено;
- прошлая сборка по списку на `main` — `main` может опережать production, и тогда в версию легли бы файлы сборки, которая не выходила, а файлы выпущенной пропали бы.

— *Следствие:* В6 — хостинг и адреса к Т-17 и О-16, сроки доменов и строка хостинга в architecture 3.12 spec, В7 — срок IP-адресов Firebase Hosting, в том числе для страницы образцов, к П-9 и privacy 4 spec, обе — в таблице 3 RUN.md, «в реестр spec». Выгрузку журналов Hosting в Cloud Logging не включать — вход T04. ## Журналы и трассы

**R07. Журналы запросов Cloud Run исключаются все — фильтром `LOG_ID("run.googleapis.com/requests")` в sink `_Default` и в каждом sink, который заведёт проект. Для разбора сбоев остаются журнал `api` и встроенные метрики Cloud Run. Трасс у первого среза нет: Cloud Trace API не включается. Журналы платформы хранятся 30 дней в бакете `us-east4`, а аудит Google Cloud в `_Required` — 400 дней в `global`, и этот срок не настраивается.** Ответы автора 2026-11-08 при планировании T04, все три — по рекомендациям. Перечень журналов — [architecture.md](architecture.md), раздел 3.4, а источники — раздел 4, прочитано 2026-11-08.
- **Исключение.** Фильтр исключения стоит в sink `_Default`, который направлен в бакет журналов `us-east4` (R04): запись идёт в назначение sink, только если «matches the sink's inclusion filter but doesn't match any of the sink's exclusion filters». Тот же фильтр — в каждом sink, который заведёт проект. `_Required` журналов запросов не получает, а его sink не меняется. Точное имя журнала в фильтре первый код сверяет по записи в проекте: страница Cloud Run показывает его только в образце записи, `run.googleapis.com%2Frequests`.
- **Что принимает Logging API.** Фильтр применяется к записи, которую Google уже принял: «Exclusion filters are applied after log entries are received by the Logging API or Telemetry API». IP-адрес доходит до Google как до обработчика, но в бакете не хранится, и платы за такую запись нет. Обещание privacy 4 spec — о журналах, которые хранятся: «без прямых идентификаторов и IP-адресов». Чтобы это читалось однозначно, слова privacy 4 spec стоит уточнить — строка В8 таблицы 3 RUN.md, «в реестр spec».
- **Остальные журналы:**
  - журналы контейнера `api` и его заданий — события `api` без идентификаторов и адресов (R26 api; architecture 3.9 api), и системные журналы Cloud Run — 30 дней в бакете `us-east4`. Журналов запросов у заданий нет: «Request logs (services only)»;
  - Admin Activity — всегда, в `_Required`, 400 дней, в `global` (Д3): «you can't configure, exclude, or disable them», а в записи — `callerIp` и почта вызывающего. Пишут его операции, которые меняют ресурсы и настройки проекта: их делают оператор и CI. Но и `SignUp` Identity Platform — создание пользователя — пишет Admin Activity, а вход Google, `SignInWithIdp`, audit-журналов не порождает. Вход `api` — через Google (R03 api), и вызывает ли что-то в проекте `SignUp` и что лежит в его записи, не проверено — первый код и строка В8;
  - System Event — тоже в `_Required`: это действия самого Google с ресурсами проекта, а не чьи-то вызовы;
  - Data Access audit не включается: по умолчанию он выключен, а в нём был бы `callerIp`;
  - Policy Denied идёт в `_Default` и хранится 30 дней: в нём — тот, кому политика отказала, и его `callerIp`;
  - журнал активности Identity Platform, `identitytoolkit.googleapis.com/requests`, не включается: «Activity logging is disabled by default», а в нём — каждый запрос входа;
  - выгрузка журналов Firebase Hosting не включается (R06); IP-адреса Firebase Auth и Firebase Hosting хранят сами (П-9; В7).
- **Для разбора сбоев** — журнал `api`: перехватчик Connect пишет метод, код, причину отказа и время, а задания — счётчики, без идентификаторов (architecture 3.9 api; T28 api); встроенные метрики Cloud Run — число запросов, задержки, экземпляры — Cloud Monitoring собирает сам и бесплатно; Error Reporting — по журналам `api`, которые хранятся. Своих метрик по журналам с метками из `httpRequest` или другими, где был бы адрес, проект не заводит: такие метрики считаются и по исключённым записям — «User-defined log-based metrics are calculated from both included and excluded logs». Оповещения — первый код, на встроенных метриках: оповещение canvas-api о нагрузке отсылало к журналам запросов, а их здесь нет.
- **Трассы.** У первого среза их нет: `api` их не пишет, а Cloud Trace API в проекте не включается. Бакет `_Trace` всё равно создаётся в `us-east4` до любой трассы, как велит R04: Cloud Run сам трассирует часть входящих запросов — «Incoming requests to Cloud Run services automatically generate traces», — выборка не настраивается, и если трассы появятся, место бакета уже будет верным. Первый код проверяет, что без Trace API трасс нет, а если есть — сверяет их атрибуты с privacy 4 spec. Трассы `api` — позже, своим решением вместе с `api`.
- **Сроки.** Бакет журналов `us-east4` — 30 дней: срок задаётся от 1 до 3650 дней. `_Required` — 400 дней, и это «Not configurable». В `spec` — строка В8, к П-9.

— *Почему:*
- поле из записи Cloud Logging не вырезать: права на поле его только скрывают — «Field-level access controls let you hide individual LogEntry fields from users», — а храниться оно продолжает. Значит, запись с адресом либо хранится вся, либо не хранится;
- код и метод запроса и так есть в журнале `api` и во встроенных метриках, а адрес для разбора сбоев не нужен;
- трассы в первом срезе нечем проверить: атрибуты автоматических трасс не описаны, а своих трасс `api` не пишет;
- 30 дней — срок по умолчанию и срок canvas-api; в журналах платформы нет ни идентификаторов, ни адресов, а одному автору для разбора сбоев нужен запас.

— *Отвергнуто:*
- оставить журналы запросов с кодом 5xx — адрес остался бы в хранимой записи;
- хранить журналы запросов коротко вместо исключения, как рекомендует privacy.md canvas-api, — адрес всё равно хранится;
- своя метрика по журналам запросов — код и метод уже есть во встроенных метриках и в журнале `api`, а метка из `httpRequest` вынесла бы адрес из исключённой записи;
- автоматические трассы Cloud Run с включённым Trace API — их атрибуты не проверены, а выборка не настраивается;
- трассы `api` через OpenTelemetry сейчас — нужен идентификатор трассы в таблице событий `api` и решение `api`, а первому срезу хватает журнала и метрик;
- 7 дней — сбой, замеченный через неделю, уже не разобрать; 90 дней — дольше, чем нужно, а личного в журналах платформы нет и так.

**R09. Контейнер `infra` отличается от контейнера `spec` одним инструментом — OpenTofu v1.13.9 в стадии `toolchain`, по `ARG` версии и суммам sha256 архивов издателя на каждую архитектуру. MPL 2.0 OpenTofu — названное исключение по R12 spec. При установке архив сверяется только с суммой, а подпись файла сумм проверяется руками `gpg` при каждом подъёме версии.** Решения автора при планировании T11, 2026-11-09: только sha256, а новая проверка CI встаёт обязательной в ruleset `main` (RUN.md, T11). Инструмент — по поправке 2026-11-08 к R11 spec, Т-29 закрыт (R08). Сверка с `spec/.devcontainer/` при переходе на новый тег это отличие не откатывает, как R12 tutor и R46 canvas-api (CLAUDE.md, Environment).
- **Стадия `toolchain`:**
  - `ARG OPENTOFU_VERSION=1.13.9` — последний релиз на 2026-11-09 (`gh release list -R opentofu/opentofu`);
  - `ARG OPENTOFU_SHA256_AMD64` и `ARG OPENTOFU_SHA256_ARM64` — из `tofu_1.13.9_SHA256SUMS` релиза, а сверка суммы идёт тем же `fetch`, что у остальных архивов, до распаковки (R34 spec). Оба архива, `tofu_1.13.9_linux_amd64.tar.gz` и `tofu_1.13.9_linux_arm64.tar.gz`, скачаны 2026-11-09 и прошли `sha256sum --check --strict`;
  - из архива берётся только `tofu` — в `/usr/local/bin`; в архиве ещё LICENSE, README.md и CHANGELOG.md. Последняя строка шага — `tofu version`.
- **Подпись.** `tofu_1.13.9_SHA256SUMS.gpgsig` проверена 2026-11-09 ключом [opentofu.asc](https://get.opentofu.org/opentofu.asc): «Good signature from "OpenTofu (This key is used to sign opentofu providers) <core@opentofu.org>"», отпечаток `E3E6 E43D 84CB 852E ADB0 051D 0C0A F313 E5FD 9F80`. Так же — при каждом подъёме версии, до того как новые суммы встанут в `ARG`: сначала отпечаток скачанного ключа сверяется с этим, а другой отпечаток останавливает подъём и становится вопросом автору — ключ, пришедший с того же сайта, что и суммы, сам по себе ничего не доказывает.
- **Лицензия.** OpenTofu — под MPL 2.0 (`LICENSE` на теге v1.13.9; [architecture.md](architecture.md), раздел 4). Это инструмент разработки и CI: он никуда не поставляется, своего кода в поставляемое не вносит, а описывает и разворачивает инфраструктуру. По R12 spec такой инструмент может нести другую лицензию, одобренную OSI, только названным исключением в решении, которое его вводит. Эта запись — такое исключение.
- **Проверка CI.** Свой job `OpenTofu` в `ci.yml` собирает стадию `toolchain` и зовёт в ней рецепты `ci-tofu-test` и `ci-tofu` своего `justfile` через `spec/tools/toolchain/toolchain.sh` (R30 spec): `tofu version -json` должен назвать версию из `ARG`. В devcontainer рецепт ловит контейнер, не пересобранный после подъёма `ARG`. В CI стадия собрана из того же Dockerfile, и проверка подтверждает только, что стадия поставила `tofu` и он запускается; вес ей даст T12, проверки модуля в том же job.

— *Почему:* T11 ставит инструмент, без которого нет ни модуля, ни его тестов. Проверки кода `infra` идут в стадии `toolchain`, поэтому инструмент — там, а не в `devcontainer`, как Go и линтер `tutor`, пока у того не было проверок Go в CI (R12 tutor). Цена — ещё около 35 МБ загрузки при каждой сборке стадии, и у проверки документов тоже. Сумма в `ARG` уже закрепляет байты архива, как у Node, just, Go и buf, а подпись подтверждает, что эти суммы выпустил OpenTofu, — это нужно один раз, когда суммы читаются.

— *Отвергнуто:*
- проверять подпись `gpg` в Dockerfile, ключом, закреплённым по отпечатку: шага, которого нет ни у одного другого инструмента, и ещё двух загрузок при каждой сборке, а байты архива сумма закрепляет и так — решение автора;
- стадия `devcontainer`: CI собирает только `toolchain`, и проверка `tofu` там бы не нашла;
- ставить инструмент на раннере action-ом, как canvas-api ставил Terraform: локально и в CI шли бы разные установки, а не одна стадия (R30 spec);
- экосистема Dependabot `opentofu` сейчас: провайдеров, которые она поднимала бы, нет до модуля, и подключать её решает T12.

— *Следствие:*
- версия OpenTofu поднимается правкой `ARG` вместе с обеими суммами и ручной проверкой подписи; Dependabot `docker` её не видит;
- пересобрать контейнер — шаг автора: сделан 2026-11-09, `tofu version` в контейнере — v1.13.9 (Д4 в таблице 4 RUN.md закрыт); проверка `OpenTofu` обязательна в ruleset `main` с 2026-11-09 — её поставил исполнитель по поручению автора;

## Cloud Run `api`

**R11. Сервис и задания `api` описывает модуль: задания он создаёт, когда `api_image` назовёт первый образ из своего реестра, а сервис — после них, когда ещё и `api_serving` это скажет; образ и версию секрета фактов в томе дальше меняет выкладка, и модуль их не трогает. Задания — список `api_jobs`, и в нём только то, что даёт бинарник `api`, пока это `migrate`; расписание Cloud Scheduler — у заданий, которым оно названо. У `api` и у выкладки — свои учётные записи с правами на свои ресурсы, а выкладка входит через пул Workload Identity Federation только из окружения GitHub `production`.** Решения автора при планировании T15 и в ней, 2026-11-09 (RUN.md, T15). Образец — `service_api.tf` и `iam.tf` canvas-api, коммит 0901af0.
- **Первый образ.** Ресурс Cloud Run без образа не создать, а образ `api` появляется в `images` только с первой выкладкой. Пока `api_image` не задан, нет ни сервиса, ни заданий, ни прав на них, а учётные записи и привязка выкладки к пулу есть: первая выкладка может положить образ. Проверка `api_image` пускает только digest из `<регион>-docker.pkg.dev/<проект>/images/`.
- **Сначала задания, потом сервис.** `api_image` создаёт задания, а сервис появляется, только когда ещё и `api_serving = true`. Первая выкладка (T24) так держит порядок R05: pull request с `api_image` — задания есть — выкладка гонит проверку конфигурации и `migrate` — pull request с `api_serving = true` — сервис встаёт на уже проверенную базу. Иначе первая ревизия приняла бы публичный трафик до миграций и до проверки фактов — решение автора в T15, по находке ревью.
- **Граница с выкладкой.** Модуль владеет формой сервиса и заданий: масштаб, ресурсы, `GET /health` как проверка запуска, учётная запись, переменные — `API_ADMISSION_RUNG=full`, `API_ADMISSION_FACTS_FILE=/etc/api/admission/facts.json`, `GOMEMLIMIT` — и том секрета `api-admission-facts`. Выкладке остаются образ сервиса и каждого задания и версия секрета фактов в томе: модуль ставит их при создании — образ `api_image`, версию `latest` — и не трогает их по `ignore_changes` (поправка 2026-11-09 к R05). Трафик модуль не описывает, как canvas-api.
- **Задания** — `google_cloud_run_v2_job` на каждую запись `api_jobs`: аргументы команды, секреты файлами — каждый томом своей последней версии, путь — в `<ИМЯ>_FILE`, как `api` читает любой секрет (R29 api), — без повторов платформой: повторять ли, решает выкладка. Секреты, которые называют задания, модуль создаёт сам, без значений: для `migrate` — `api-migrate-database-url` и `api-migrate-openfga-database-url`. Проверка конфигурации, задание после выкладки и задание сроков хранения встанут в список, когда их назовёт релиз `api`. Задание, добавленное позже, создаётся с `api_image`, первым образом, и получает выкаченный, когда выкладка ставит образ каждому заданию: задание входит в список с релизом `api`, в котором есть его команда, и выкладка этого релиза идёт за его `apply` (R05). Секрет, которого список больше не называет, модуль отпускает, `deletion_policy = "ABANDON"`: забывает его, а значение остаётся у того, кто его держит.
- **Расписание** — учётная запись `api-scheduler` с `roles/run.invoker` на заданиях по расписанию и `google_cloud_scheduler_job`, который вызывает `…/jobs/<имя>:run` в UTC; ничего из этого нет, пока у задания нет `schedule`.
- **Учётные записи и права:**
  - `api-run` — сервис и задания; читает секрет фактов и секреты заданий;
  - `api-deploy` — выкладка: `roles/artifactregistry.writer` на `images`, `roles/secretmanager.secretVersionAdder` на секрете фактов, `roles/iam.serviceAccountUser` на `api-run` и своя роль из прав `run.services.get` и `.update`, `run.revisions.get` и `.list`, `run.operations.get`, `run.jobs.get`, `.update`, `.run` и `.runWithOverrides`, `run.executions.get` и `.list` — на сервисе и на каждом задании, а не на проекте. Создавать и удалять сервисы, менять, кто их вызывает, и сама читать секреты она не может. Но то, что идёт как `api-run`, читает секреты `api`, и учётная запись, которая ставит образ `api`, дотянется до них так: выкладке доверено то же, что `api`, а её дверь — одно окружение одного репозитория. Права сверены с документацией Cloud Run ([architecture.md](architecture.md), раздел 4); `run.operations.get` и `run.revisions.list` даны на ресурсах, как у canvas-api, чья выкладка на них работает, — первая выкладка (T24) проверит это и здесь;
  - выкладку пускает `roles/iam.workloadIdentityUser` только для subject `<github_oidc_subject_prefix>:environment:production` — заданий окружения `production` репозитория `infra` (R106 spec). Пул, его провайдер и учётную запись, которая применяет конфигурацию, создаёт `bootstrap.sh` (T17), а модуль называет их по ID;
  - `allUsers` вызывает сервис: кого пустить, решают проверки `api`.
- **Размер** — переменные: от 0 до `api_max_instances`, 1 по умолчанию, 1 vCPU, `1Gi`, 40 запросов на экземпляр, `60s` на запрос — под `API_HTTP_WRITE_TIMEOUT` `api`. Проверки держат пределы Cloud Run: 1, 2, 4, 6 или 8 vCPU, не меньше 2 GiB при 4 и 4 GiB при 6 и 8, запрос — до 3600 с, задание — до 168 часов ([architecture.md](architecture.md), раздел 4).

— *Почему:* всё, кроме того, что меняет каждая выкладка, лежит в одном месте и проверяется тестами; образ, которого нет в реестре, не придумывается; задание с выдуманной командой не создаётся (RUN.md, правило 2); права выкладки — ровно её шаги, на её ресурсах.

— *Отвергнуто:*
- образ-заглушка Google `hello`, как у canvas-api: он не проходит правило о production-образах (RULES.md, Production images) и отвечал бы в production до первой выкладки — решение автора;
- сервис и задания создаёт выкладка через `gcloud`, а модуль держит только учётные записи и права: форма сервиса ушла бы из OpenTofu в скрипты — решение автора;
- все задания сразу, по именам, которых `api` ещё не дал, или задания своей задачей потом — решение автора: список, в котором только то, что есть;
- права выкладки на проекте или готовая роль разработчика Cloud Run: в ней и удаление сервиса, и смена IAM;
- сервис сразу с заданиями — первая ревизия до миграций — или сервис сразу, но без права `allUsers` его вызывать — ревизия до миграций всё равно запущена и читает непроверенные факты — решение автора.

## Firebase и публикация на Hosting

## Разовый шаг оператора

**R13. `tofu/bootstrap.sh` один раз, правами оператора, делает то, чего конфигурация не может сделать сама: проект и его привязку к платёжному аккаунту, бакет состояния, пул Workload Identity Federation с провайдером `github`, учётную запись конфигурации `infra-config` с её правами и две свои роли, которые даёт модуль. Провайдер пускает только токены репозитория `infra` — по числовым ID владельца и репозитория, — а `infra-config` берут только задания окружения GitHub `production-config`. Роли `infra-config` перечислены, а не Owner; менять, кто что держит на проекте, она может только для двух ролей публикации и не может править ни одну роль.** Решения автора при планировании T17 и в ней, 2026-11-09 (RUN.md, T17). Образец — `infra/bootstrap.sh` canvas-api, коммит 0901af0 ([architecture.md](architecture.md), раздел 4).
- **Откуда значения.** Скрипт читает `project_id`, `region`, `workload_identity_pool_id`, `github_oidc_subject_prefix` и `budget_currency` из `tofu/production.auto.tfvars`, а `bucket` — из `tofu/backend.hcl`: оба файла пишет T23, и каждое значение лежит в одном месте. Пустое значение, `REPLACE…` или значение не той формы, что берёт модуль, — отказ до первого вызова `gcloud`. Платёжный аккаунт приходит из `TF_VAR_billing_account`, как в `plan`, и скрипт его нигде не печатает, даже в ошибке `gcloud`: там он заменён словами «<billing account>», как у canvas-api.
- **Оплата.** Валюта аккаунта сверяется с `budget_currency` до того, как что-либо создано: бюджет в другой валюте отказал бы только на первом `apply`, после мержа. Проект без оплаты привязывается к `TF_VAR_billing_account`; проект, который уже платит через другой аккаунт, скрипт не переносит и останавливается: бюджет считает траты того аккаунта, через который проект платит. Проект, помеченный к удалению, скрипт тоже не трогает: вернуть его — шаг человека.
- **API** — `serviceusage`, `cloudresourcemanager`, `iam`, `sts`, `iamcredentials` и `storage`, без которых ничего ниже не создать; `observability` — заранее, его настройки какое-то время отказывают после включения (canvas-api); `run`, `firebase` и `firebasehosting` — ради прав своих ролей: «a permission might not be available for use in custom roles if you have not enabled the API for the service» (IAM, Create and manage custom roles, прочитано 2026-11-09).
- **Свои роли** — `apiDeployer`, одиннадцать прав выкладки `api` (R11), и `hostingPublisher`, восемь прав публикации (R12). ## Выкладка `api`

**R15. Выкладку `api` по списку делает `tools/deploy/api.sh` — bash, по шагам R05, на том, что называют выходы модуля. Команды: `image` — образ релиза и его digest; `release` — новый релиз целиком; `facts` — только факты. Тег релиза, который принимает трафик, — тег его образа в реестре. Какие задания запускать и когда, говорит роль задания в `api_jobs`, а не его имя.** Решения автора при планировании T19, 2026-11-09 (RUN.md, T19).
- **Значения** — из `tofu output -json` того же коммита после `apply`: `project_id`, `region`, `image_repository`, `api_service_name`, `api_jobs`, `admission_facts_secret`, `admission_facts_file`. Выхода, которого нет, и заданий не той формы — отказ до первого шага. Что сервиса нет, `gcloud` говорит кодом `NOT_FOUND` или словами «Cannot find service»; любая другая ошибка чтения сервиса — отказ.
- **`image`:**
  - файлы релиза `api` скачиваются и проверяются снова — `tools/deploy-check/fetch.mjs`, то же `releaseFile`, что у проверки списка: sha256 и `release-verify` (R05, R14);
  - бинарник — файлом `api` в контексте сборки `binary`, основной контекст пуст: `docker build --target release --build-context binary=<папка> -f <Dockerfile релиза>` (README `api` v0.1.5; R28 api);
  - образ — для `linux/amd64`, платформы бинарника и Cloud Run, в `<реестр>/api:<тег релиза>`, а digest — тот, что сообщил push. Тег держит образ от очистки (T14) и говорит, какой это релиз;
  - образ, который реестр уже держит под тегом релиза, — от прошлой выкладки того же релиза — берётся как есть: собранный заново, он получил бы другой digest, и тег ушёл бы с образа, который, может быть, принимает трафик.
- **`release`** — шаги R05 по порядку, и неудача любого останавливает выкладку:
  1. если сервис есть, тег релиза, который принимает трафик, — тег в реестре того digest, на котором стоит ревизия с трафиком. Нет тега, их больше одного, тег не точный или трафик поделён между ревизиями — отказ с причиной. Новый релиз ниже — отказ, тот же — можно. Теги сравниваются по числам. Списка заданий без роли `migrate` выкладка не пускает;
  2. `image`;
  3. новая версия секрета фактов из `deploy/production/facts.json`;
  4. образ — заданиям `check` и `migrate`, и только им: задание по расписанию или `after` с новым образом запустило бы новый релиз на базе, которую миграции, может быть, не дошли;
  5. задания `check`, затем `migrate` — каждое до конца, `gcloud run jobs execute --wait`;
  6. ревизия по digest с этой версией фактов, `--update-secrets <файл фактов>=<секрет>:<версия>`, без трафика; когда она — готовая ревизия сервиса, весь трафик ей, по имени, `update-traffic --to-revisions=<ревизия>=100`: ревизия, созданная тем временем кем-то другим, трафика не получит;
  7. образ — заданиям `after` и по расписанию: задание, добавленное с новым релизом, создано с первым образом (R11); затем задания `after`.

  Пока модуль не создал сервис — первая выкладка, только `api_image` (R11), — шаги 1, 6 и задания `after` пропускаются, а образ получают все задания, и рецепт это говорит.

## Вход в production

**R16. Вход в production-проекте платформы — Firebase Auth с Identity Platform. Модуль переводит проект на неё и держит её настройки: разрешённые домены — `<проект>.firebaseapp.com` и `<проект>.web.app`, вход — только окном Google, журнал активности выключен. Вход через Google с его OAuth-клиентом и экраном согласия оператор включает в консоли Firebase после первого `apply`: секрета клиента нет ни в репозитории, ни в состоянии. Пользователями входа `api-run` управляет своей ролью `signInUsers` из `bootstrap.sh`, а проект узнаёт из `API_FIREBASE_PROJECT_ID`.** Решения автора при планировании T27, 2026-11-09, все четыре — по рекомендациям (RUN.md, T27). Источники — [architecture.md](architecture.md), раздел 4, прочитано 2026-11-09. Образца нет: у canvas-api к коммиту 0901af0 входа в коде не было, только решения о нём (R14 и R34 canvas-api).
- **Identity Platform** — `google_identity_platform_config` в `tofu/sign_in.tf`, из провайдера `google`, и `identitytoolkit.googleapis.com` в списке API:
  - настройки Firebase Auth кодом пишутся только через неё: ресурс «enable[s] Google Cloud Identity Platform (GCIP) (which is the backend for Firebase Authentication)», и только в проекте на Blaze;
  - переход не отменяется, а в Google Cloud ресурс не удаляется: `destroy` только убирает его из состояния, и `deletion_policy` провайдер не читает (исходник v8.10.0);
  - цена: вход через Google — Tier 1, до 50 000 активных пользователей в месяц бесплатно, дальше $0.0055 за каждого. После перехода проект на Blaze платит «for usage beyond the free tier of 50,000 monthly active users».
- **Настройки:**
  - разрешённые домены — весь список: адрес Firebase, на котором открывается окно входа `app` (`authDomain`, R09 app), и origin `app`. Домен, поставленный в консоли, следующий `apply` уберёт, и домен канала предпросмотра Hosting тоже: `app` выходит только в live-канал сайта (R06), а свой домен встанет в список, когда будет куплен. Адрес `web.app` модуль берёт из ID сайта Hosting, а не из ID проекта, чтобы два адреса не разошлись. Ни `localhost`, ни `127.0.0.1`: с ними окно входа проекта платформы открылось бы с любой локальной страницы, а у локального запуска свой проект Firebase ([architecture.md](architecture.md), разделы 2.6 и 3.5);
  - вход по почте, по телефону и анонимный — выключены: сервис входа не держит ни пароля, ни почты, ни номера (R03 api). Повторные адреса почты выключены, журнал активности — тоже, явно, а не умолчанием, и каждый sink его исключает (поправка 2026-11-09 к R07). Арендаторов и второго фактора нет;
  - `disabled_user_deletion = true`: пользователя удаляет только `api`, вместе с его аккаунтом и после отзыва токенов (R03 api), а `app` удаляет аккаунт через `api`. Регистрация окном Google открыта, `disabled_user_signup = false`.
- **Вход через Google** — шаг оператора ([architecture.md](architecture.md), раздел 3.3):
  - OAuth-клиент и экран согласия программно не заводятся: API, которым их заводили, Google закрыл — «The IAP OAuth Admin API was shut down on March 19, 2026», — а провайдер в 8.0.0 убрал `google_iap_brand` и `google_iap_client`. `google_iam_oauth_client` — только для Workforce Identity Federation;

## Выпуск сборки `app`

## Ключи eval

**R20. Ключи платформы для eval — секреты модуля `eval-key-<код поставщика>`, по одному на код `eval_providers`: `eval-key-anthropic` и `eval-key-openai`. Без репозиториев eval нет ни секретов, ни пула, а пул, сделанный прежде, никого не пускает.** Решение автора при планировании T22, 2026-11-09 (RUN.md, T22): кто делает пул.
- **Секреты** — `tofu/secrets.tf`, рядом с остальными секретами модуля, а кто их читает — `tofu/eval.tf`:
  - репликация по выбору, `var.region`, как у всех секретов модуля (R04): региональный секрет читается только из своего региона, а runner GitHub — не там (R120 spec);
