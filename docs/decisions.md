## Region

**R04. Everything `infra` keeps in a region is in `us-east4`, by R109 spec: the Cloud Run services and jobs, the Artifact Registry repository, the secrets with user-managed replication, the log bucket with the sink `_Default`, and the trace bucket `_Trace`, created before the first trace. `_Required` stays in `global` while there is no Google Cloud organization.** The region of the platform — the US, one place for all learners — was decided by the author in `spec`, R109 spec, by the recommendation of the row В3 of this repository; here is what it means for each resource of `infra`. The sources are [architecture.md](architecture.md), section 4, read 2026-11-08.
- **The region of each resource** ([architecture.md](architecture.md), section 3.1):
  - the Cloud Run services and jobs — `us-east4`, beside Neon `aws-us-east-1` of the database of `api`: both are in Northern Virginia;
  - the Artifact Registry repository — regional, `us-east4`: the place of a repository does not change after it is created, and a multi-region is slower;
  - the Secret Manager secrets — with user-managed replication, at the place `us-east4`. Automatic replication replicates data without restrictions, and a regional secret is accessible only from its own region: the eval key by Т-28 would be read by CI on GitHub;
  - the log bucket — its own, in `us-east4`, and the sink `_Default` is directed into it: Cloud Logging creates the bucket `_Default` in `global`, and its place does not change;

  - `_Required` — in `global`: only a setting of the organization or of a folder before the project is created gives it a region, and an organization is tied to a domain, and there is none until О-16. The debt is Д3 in table 4 of RUN.md.
- **Not here:** the region of the database of `api` — Neon `aws-us-east-1` — is kept by `api` (Д127 in table 4 of RUN.md `spec`); Firebase Auth processes data only in the US in any region; the hosting of the build of `app` is chosen by T03, and Firebase Hosting is a global service; R109 spec does not decide the region of the AI calls (R96 spec).

The region of each resource is the one the row recommended, and R109 spec repeats it.

— *Rejected:*

- the multi-region `us` for Artifact Registry and the buckets: there is one region anyway, and a multi-region repository is slower — "operations in multi-region repositories may be slower than single-region repositories";
- regional secrets: CI on GitHub, outside `us-east4`, would not read the key;

- setting up a Google Cloud organization before the first deployment, so that `_Required` stands in the region: it needs a domain, and the domain waits for О-16 — the author's decision in planning T01.

## Rollout

**R05. The rollout list is a JSON file `deploy/production.json` in `infra` with its own schema, and beside it are the values of `/deployment.json` and the facts file. A pull request edits it by hand, and the merge into `main` is the deployment, as long as `main` stands on this commit. The CI of the pull request checks everything without access to production, and an `api` release lower than the one rolled out is refused both by CI and by the deployment. The revision of `api` gets the facts file as a volume — a version of a Secret Manager secret pinned in the revision —, and the admission rung as an environment variable.** The author's answers of 2026-11-08 in planning T02, all four by the recommendations; how the revision gets the facts the author decided anew the same day, after the review of T02: the text of `spec` names the facts a file. This is what R106 spec and its 2026-11-08 amendment left to `infra` (architecture 3.11 spec). What the list looks like and how the deployment goes step by step is [architecture.md](architecture.md), section 3.2.
- **The list** is `deploy/production.json`, format 1, and its JSON schema is in `deploy/schema/`. A field the schema does not know is an error. The list names:
  - the release of `api` — the tag, the name and sha256 of the binary `linux_amd64`, and the sha256 of the `Dockerfile`; the list does not name module packages — the build stage of `api` puts them into the image by `modules.json`, embedded in the binary (R106 spec; R07 api);
  - the release of `app` — the tag, the name and sha256 of the build's archive, and the sha256 of the file `/deployment.json`, as Т-19 says;
  - the lowest rung of the admission of models of `api` — the code of a rung from `tutor`: `author` or `full` (`admission/models.go` `tutor`, `main` 28ea592). `infra` keeps it beside the list (the 2026-11-08 amendment to R106 spec), and the list names it explicitly, although without a value `api` takes "full" anyway (R25 api).

  Beside it lie `deploy/production/deployment.json` — the values of `/deployment.json` in format 1 (R09 app; R85 spec) — and `deploy/production/facts.json` — the deployment facts file in the form `facts` of the admission table, whose type and parsing are `tutor`'s ([the text of the admission table](../spec/admission/README.md), section 5; R57 tutor). The list does not name the configuration of Terraform or OpenTofu: it is code of the same commit of `infra` (Т-29).
- **Editing** is a pull request of `infra`, by hand. Its review is the approval of the deployment: the environment has no required approval, as in canvas-api, where the environment `prod` has only the rule of the branch `main` (GitHub's API, read 2026-11-08).
- **The checks of the pull request's CI** — without access to production:
  - the list — by its schema;
  - each release file — the binary of `api`, its `Dockerfile`, the archive of `app` — is accepted by `just -f spec/justfile release-verify <repository> <tag> <file>` (R77 spec), and its sha256 equals the one named in the list: the recipe does not print the digest (`spec/tools/release/verify.mjs`). If Sigstore or GitHub does not answer, the file is refused (R77 spec);
  - `deployment.json` — by `deployment.schema.json` from the archive of this build, and its sha256 is the one in the list;
  - `facts.json` — by the vocabulary of facts of the admission table of the `spec` tag that the submodule of `infra` stands on. This is an early sign: the file is finally checked by `api` at start, by its own version of the table, and a fact unknown to it is an error (R25 api), — so the deployment also checks it with the image of the new release before the migrations (the steps below; В4);
  - the rung — only `full`: the rung "author" is only for the first app, and «любое развёртывание, даже где учится один автор, передаёт „полную“» (R25 api; the 2026-11-08 amendment to R76 spec);
  - the tag of `api` — not lower than in the list on `main`; the same one is allowed.
- **The deployment** — after the merge, only if `main` still stands on the commit of the list. The first job checks this, and each next one does on a retry: otherwise a rerun of an old run would roll production back (R45 canvas-api). It does only what changed:
  - a new release of `api` — the tag of `api` is not lower than that of the revision that now takes the traffic: `main` can be ahead of production if the previous deployment did not complete, and the pull request could have passed CI against the former `main`. Then a repeat of `release-verify` and sha256; the image by the release's `Dockerfile` — into Artifact Registry `us-east4` (R04), by the digest from the push; the configuration check with the image of the new release — the command from В4; the migrations job of both databases with the same image; the revision by digest — first without traffic, then with all the traffic; the job after the deployment (R106 spec with the 2026-11-08 amendment);
  - only the facts or the rung — a new version of the facts secret and a new revision on the image that is already rolled out, by its digest: without a build, without migrations and without `release-verify` — the release files did not change. So removing a fact waits neither for Sigstore nor for a build (R96 spec);
  - a new release of `app` — the release of the build on the hosting (R85 spec; T03).

  Step by step — section 3.2. A deployment that did not complete is repeated by rerunning its jobs, or fixed forward by a new pull request.
- **The facts and the rung.** The deployment puts `facts.json` as a new version of a Secret Manager secret — with user-managed replication, in `us-east4` (R04) — and mounts exactly this version into the revision as a volume, and sets the path to the file and the rung as environment variables. Cloud Run lets one choose the version of a secret mounted as a volume: "You can select a specific version if you want", and by default it takes the latest ([Configure secrets](https://docs.cloud.google.com/run/docs/configuring/services/secrets), updated 2026-10-30, read 2026-11-08). The version is pinned in the revision, and a rollback of the revision reproduces it. There are no secrets in the facts (R25 api), and the secret here is only a way to give the revision a file: `spec` names the facts a file of the deployment configuration of `api`, whose type and reading are `tutor`'s ([the text of the admission table](../spec/admission/README.md), section 5; architecture 3.6 spec). `api` reads secrets from a file by the path in the variable `X_FILE` (R26 api) — it will read the facts file the same way. The names of the variables are the row В4 of table 3 of RUN.md, «в реестр spec».
- **Rollback.** `api` — only forward, by a new release: neither CI nor the deployment lets a lower tag through (R106 spec; Т-19). The build of `app` — by a pull request that returns its block of the list to the former values: a revert of a whole commit that also raised `api` would lower `api` and be refused. A build of `app` that has moved to a new version of the module format — only forward, and the author checks this in review. The facts and the rung — by a pull request with the former values: a new revision on the same image. To close platform AI urgently — remove a fact by the same kind of pull request (R96 spec).
- **Self-hosting** keeps the same kind of `deploy/` folder with its own `deployment.json` and facts and goes the same way in its own project and its own registry (R105, R106 spec; Т-20). So the checks and the steps of the deployment are recipes that run without GitHub Actions too; their names and the workflow are the first code of `infra`.

— *Why:*
- JSON with a schema — as `modules.json` of `api` and `/deployment.json` itself: the parsing is unambiguous, and the check by a schema is the same as the neighbours';
- a pull request by hand — the shared `release.yml` of `.github` v0.1.21 has no outputs, and `api` and `app` have no releases yet: there is nothing to chain the deployment to a release with, as canvas-api did, and each release passes the author's review anyway;
- refusing an `api` release lower — both in CI and in the deployment: CI shows the error before the merge, and the deployment matches against what is actually rolled out. Otherwise a revert of the list would bring back an image of `api` with an old release of `modules`, where a withdrawn version would become current again (Т-19);
- the facts file as a volume — so the text of `spec`, which names them a file, holds, and the secret version is pinned in the revision, as a variable's value is. `spec` names the rung a value of the configuration (the 2026-11-08 amendment to R76 spec), and a variable is enough for it;
- deploying what changed — removing a fact must not wait for a build, migrations and Sigstore, and a rollback of `app` must not wait for a rebuild of `api`.

— *Rejected:*
- YAML — it has ambiguities of parsing, and the neighbouring files are JSON;
- variables of Terraform or OpenTofu — the list would depend on Т-29, and the image, the jobs and the release of the hosting do not fit into Terraform: canvas-api kept the image outside Terraform ([architecture.md](architecture.md), section 4);
- a required approval of the environment — a second approval by the same author on top of the pull request's review;
- pull requests from the services' releases — the CI of `api` and `app` would need a token to write to `infra`. It can be added later, on top of this path;
- a warning instead of a refusal, and "do not check" — a revert of the list would then blindly bring back a withdrawn version of a module;
- the facts as an environment variable, JSON on one line, — the author's first answer in planning: `spec` names the facts a file, whose type and reading are `tutor`'s, and the normative text of `spec` would have to be edited (the review of T02);
- the facts as a file in the image — «в образ и в git `api` они не входят» (R25 api), and a change of a fact would wait for a new build;
- deploying everything on each merge — removing a fact would wait for Sigstore and migrations, and a rollback of `app` would rebuild `api`.

— *Consequence:* В4 — the names of the variables and the configuration check for `api`, В5 — the format of `/deployment.json` in `spec` by the first code of `infra` (R85 spec), both in table 3 of RUN.md, «в реестр spec». ## Hosting and domains

**R06. The build of `app` is served by Firebase Hosting — the default site of the platform's project. The first deployment has no domain of its own: `app` lives at the project's `web.app` address, and `api` at its own Cloud Run address `*.run.app`, with CORS for the exact origin of `app`. When to buy the main domain and the widgets' domain, `spec` decides (О-16, Т-17); the recommendation of `infra` is together after О-16, before the public launch (В6).** The author's answers of 2026-11-08 in planning T03, all three by the recommendations. Т-17 left the choice of the hosting of the build of `app` to this task — by what the hosting writes to the logs (the answer to В13 `spec`; R01). How it is built is [architecture.md](architecture.md), section 3.3, and the sources are section 4, read 2026-11-08.
- **Hosting** — Firebase Hosting, the project's default site, the Blaze plan: on the free Spark the site is turned off when a quota is exceeded, and the project has billing anyway. Storage up to 10 GB and transfer up to 10 GB a month are free. Blaze has no spending cap, so the project's budget with an alert is set by the first code of `infra` (architecture 3.11 spec).
- **The release of the build** is the step of the deployment of `app` from R05. The rollout assembles the release folder: the archive of the new build, the `assets/` of the build that is now released on Hosting, and `/deployment.json` from `deploy/production/deployment.json`. Then it writes `firebase.json` and releases everything as one version of Hosting: "The content and configuration served by each channel is packaged into a version object".
  - **The previous build** is the one that is released now, not the one named in the list on `main`: `main` can be ahead of production if the previous deployment did not complete (R05). The rollout writes the tag of the released build into the Hosting release and reads it from there; how — the first code. Its archive passes the same checks as the new one: `release-verify` and sha256 — only a checked file gets into the job that reaches production (R05). The first release has no previous build, and the folder is only the new build.
  - The rollout puts in the files of the previous build itself: a version is a full set of files, and Т-17 says to keep the files of the previous release. canvas-api did not do this, and its next release removed the files of the previous one.
  - `headers`: on all paths — `X-Content-Type-Options: nosniff` and HSTS; on all paths outside `/assets/**` — the CSP by the archive's `csp.json`, with `{api}` and `{authDomain}` from `deployment.json` and with `frame-ancestors 'none'`, and `Cache-Control: no-cache`; on `/assets/**` — `immutable` (Т-17; architecture 3.7 app). Not by the path `index.html`: Hosting matches headers against the path of the request before rewrites, and an SPA path rewritten to `index.html` would otherwise be left without the CSP and without `no-cache`;
  - the SPA rewrite to `index.html` — only outside `/assets/**` and `/deployment.json`: Hosting rewrites a path only if there is no file at it, and without the exception it would serve `index.html` for a request for a file that is gone;
  - `Cross-Origin-Opener-Policy: same-origin` is not sent: it breaks the Firebase sign-in window (Т-17).

  After the release the rollout checks the responses: the bytes of `index.html`, the headers on `/`, on an SPA path and on a file in `/assets/`, a `404` for an unknown file in `/assets/`, as `ci-hosting-check` of canvas-api does.
- **Rollback** — by R05: a pull request that restores the earlier block `app` of the list. A rollback by a version in the Firebase console is not used: the list stays the truth.
- **Logs.** Firebase Hosting itself keeps IP addresses — "Hosting retains IP data for a few months" —, and this is not configurable, and the service is global: the region of R04 does not hold it. Do not turn on the export of Hosting's logs to Cloud Logging: it is optional, and its entries have `remoteIp`. Firebase's period is the row В7 of table 3 of RUN.md, «в реестр spec», for П-9 and privacy 4 spec. The hosting is a processor of data (privacy 2 spec).
- **Addresses:**
  - the first deployment has no domain of its own: `app` — `<project>.web.app`, `api` — `*.run.app`. So it was in canvas-api too: «свой домен не нужен закрытой бете по приглашениям, а domain mapping Cloud Run в Preview» (R55 canvas-api);
  - the default site answers at two addresses, `web.app` and `firebaseapp.com`, with the same content. The origin of `app` is only `web.app`: it is named by the CORS of `api` and by `/deployment.json`, and `app` from `firebaseapp.com` will not reach `api`. The project's `firebaseapp.com` is the `authDomain` of Firebase Auth: `app` signs in by a window, the sign-in page is `/__/auth/handler` on it, and there is no need to keep it on `web.app` (R09 app);
  - the rollout adds `<project>.web.app` to the authorized domains of the Firebase project (Т-19) and does not remove the domains that Firebase itself puts there;
  - when a domain of its own appears, Hosting gets it, and how `api` gets it is decided at the same time: Cloud Run domain mapping is in Preview. For the widgets' domain of stage 4 `infra` prepares nothing now: where the widgets' bundles are hosted is Т-17.
- **The samples page of `canvas`** will move to Firebase Hosting when it moves (R25 spec) — as a separate site of the project with its own origin: the sign-out of `app` erases all the storage of its origin (architecture 3.7 app), and Hosting keeps several sites in one project. Children's samples are made with it too (R25 spec), so then the IP addresses of the devices on which they are made will also get into Firebase's logs for the same period — this is in В7.
- **Self-hosting** — any hosting that sends its own headers, by the same steps; without its own headers — weaker protection (Т-17).
- **Not checked — the first code.** Whether Hosting's rewrites can exclude `/assets/**` and `/deployment.json`: the documentation refers to the syntax of glob and RE2, and RE2 has no lookahead. If they cannot, the rewrites name the SPA paths explicitly. And whether Hosting itself sends HSTS or `Cross-Origin-Opener-Policy`: the check after the release matches the response headers.

— *Why:*
- of the options that send their own headers and release the files with the headers as one version, Firebase Hosting alone requires neither code of its own nor a domain of its own, and it is already in the same project as Firebase Auth;
- a closed slice needs no domain of its own, and О-16 says to check the trademark before registering a domain (product 13 spec);
- different origins — the requests to `api` do not go through the hosting, and its logs do not see each request of a learner; `api` has already described CORS (architecture 3.9 api).

— *Rejected:*
- Cloud Storage with an external load balancer and Cloud CDN — for a backend bucket the load balancer's log "is automatically enabled and cannot be disabled", a certificate needs a domain of its own, and there is no release as one version;
- Cloud Run with a static server — it is a service with its own code and release (R105 spec), and `infra` holds no code of services (CLAUDE.md, The component). For static content Google names Firebase Hosting and Cloud Storage;
- Cloudflare Pages — one more processor outside Google, no retention period of IP addresses was found in its terms, and without a `404.html` it serves `index.html` for any path;
- GitHub Pages — sends no headers of its own: "We don't support this feature today so a `meta` tag unfortunately is the only way" (a GitHub employee), and Т-17 rejected such a hosting;
- a domain of its own for the first deployment — against О-16;

## Logs and traces

**R07. The request logs of Cloud Run are all excluded — by the filter `LOG_ID("run.googleapis.com/requests")` in the sink `_Default` and in every sink the project sets up. For the analysis of failures the log of `api` and the built-in metrics of Cloud Run remain. The first slice has no traces: the Cloud Trace API is not turned on. The platform's logs are kept for 30 days in a bucket in `us-east4`, and Google Cloud's audit in `_Required` for 400 days in `global`, and this period is not configurable.** The author's answers of 2026-11-08 in planning T04, all three by the recommendations. The list of logs is [architecture.md](architecture.md), section 3.4, and the sources are section 4, read 2026-11-08.
- **The exclusion.** The exclusion filter stands in the sink `_Default`, which is directed into the log bucket in `us-east4` (R04): an entry goes to the sink's destination only if it "matches the sink's inclusion filter but doesn't match any of the sink's exclusion filters". The same filter is in every sink the project sets up. `_Required` does not get request logs, and its sink does not change. The exact name of the log in the filter the first code matches against an entry in the project: the page of Cloud Run shows it only in an example entry, `run.googleapis.com%2Frequests`.
- **What the Logging API takes in.** The filter applies to an entry that Google has already received: "Exclusion filters are applied after log entries are received by the Logging API or Telemetry API". The IP address reaches Google as a processor, but is not kept in the bucket, and there is no charge for such an entry. The promise of privacy 4 spec is about the logs that are kept: "without direct identifiers and IP addresses". So that it reads unambiguously, the words of privacy 4 spec should be refined — the row В8 of table 3 of RUN.md, «в реестр spec».
- **The other logs:**
  - the logs of the container of `api` and of its jobs — the events of `api` without identifiers and addresses (R26 api; architecture 3.9 api) —, and the system logs of Cloud Run: 30 days in the bucket in `us-east4`. Jobs have no request logs: "Request logs (services only)";

It is written by the operations that change the project's resources and settings: the operator and CI make them. - **Periods.** The log bucket in `us-east4` — 30 days: the period is set from 1 to 3650 days. `_Required` — 400 days, and this is "Not configurable". In `spec` — the row В8, for П-9.

- the code and the method of a request are in the log of `api` and in the built-in metrics anyway, and the address is not needed for the analysis of failures;
- in the first slice there is nothing to check traces with: the attributes of automatic traces are not described, and `api` writes no traces of its own;
- 30 days is the default period and the period of canvas-api; the platform's logs have neither identifiers nor addresses, and one author needs a margin for the analysis of failures.

## The checks of the rollout list

**R14. The rollout list is checked by the schema `deploy/schema/production.schema.json` and by the check `tools/deploy-check/`, in Node: the six items of R05 — the schema; the release files, by `release-verify` and sha256; `deployment.json`, by the schema of its build; the facts, by the vocabulary of `spec`'s admission table; the rung `full`; the tag of `api` no lower than on `main` — and also the name of `api`'s binary, which the schema cannot express. In CI the job `Deploy` runs its tests in every pull request, and the list itself when a pull request changes what checks it. One dependency — ajv 8.20.0, by the lock file of `tools/`.** The author's decisions when planning T18, 2026-11-09 (RUN.md, T18).
- **The schema** — JSON Schema 2020-12, format 1; a field the schema does not know is an error at every level. It holds the form: exact tags `vX.Y.Z`, sha256 of 64 lowercase hexadecimal digits, the binary's name `api_<tag>_linux_amd64`, the name of `app`'s archive — `*.tar.gz` with no path, the rung — `author` or `full`, both rungs of `tutor`. What the schema cannot express, the check holds: the tag in the binary's name equals the release's tag — a seventh check beyond the six items of R05 — and the rung is only `full`.
- **The check** — `node tools/deploy-check/main.mjs [--base <ref>] [<directory>]`, the recipe `just deploy-check`; without `deploy/production.json` it says there is nothing to check. Each refusal names what was found and what was expected. Each check runs whatever the earlier ones found, and all the refusals are named, not the first: each release file by a check of its own, the sha256 of `deployment.json` by its own; a check that needs a rejected file says it did not run. The exception is the schema's refusal: after it the list cannot be read further. A pull request does not delete a list that exists on the base: otherwise the next list would have nothing to be compared with, and `api` would go back:
  - the release files are downloaded from the release's public address on GitHub together with `.sigstore.json`; the sha256 is compared with the one the list names, and `just -f spec/justfile release-verify` accepts the file (R77 spec). If GitHub or Sigstore do not answer, the file is rejected;
  - `deployment.json` is checked by the schema `deployment.schema.json` from the root of this build's archive, and a schema of a dialect other than 2020-12 is a refusal. Until T26 this is the file's only schema (R85 spec with its 2026-11-08 amendment; В12 of table 3 of RUN.md);
  - the facts — by `$defs/declared_facts` of the schema of the answer vector in `spec/admission/schemas/`, and the providers and the codes of the facts from the vocabulary of `spec/admission/admission-table.json`, at the submodule's tag. This is an early sign: `api` checks the file by its own table at its start (R25 api);
  - the tag of `api` is compared with the tag of the list on the base by numbers, not as text: v0.10.0 is higher than v0.9.0. A base without a list has nothing to compare with.
- **ajv** — with the settings of `spec` itself (`spec/tools/format-check/schemas.mjs`): all errors; an unknown keyword is an error; `format` only an annotation, as in 2020-12 by default; `strictTypes` and `strictTuples` off — otherwise ajv rejects `spec`'s admission schemas. Dependabot raises the packages: the ecosystem `npm`, the directory `/tools`.
- **Tests:**

**R16. Sign-in in the platform's production project is Firebase Auth with Identity Platform. ## The release of the build of `app`

**R17. The build of `app` is released onto Firebase Hosting by a script of its own, `tools/deploy/app.mjs`, through the REST API of Hosting, not the Firebase CLI. It recognizes the released build by the release's message, keeps its `assets/` in the new version, and checks the site's answers after the release. The sources — [architecture.md](architecture.md), section 4, read 2026-11-09.
- **The steps of `release`** — by R06:
  1. the list — by its schema, and `production/deployment.json` — of the sha256 that the list has, and no more than the 16 KiB that `app` reads (architecture 3.7 app). These are the same functions of `check.mjs` as the pull request check's;
  2. the new build's archive — again `releaseFile` from `check.mjs`, sha256 and `release-verify`. Unpacking comes only after the archive's listing showed nothing but files and folders, with no links and no paths outward; at the root — `index.html`, `assets/` with a file, `deployment.schema.json` and `csp.json`, and no `deployment.json` of its own. `deployment.json` — by the build's schema;
  3. the previous build — by the message of the live channel's release, `app <tag> <archive> <sha256>` and, after `keeping`, the build whose `assets/` it kept (the second 2026-11-09 amendment to R06).   5. the version — `versions.create` with the configuration, `populateFiles` in batches of 1000 paths, the upload of what Hosting asked for, `FINALIZED`, and `releases.create` with this build's message. Hosting names a file by the sha256 of its bytes in gzip, and a version is a full set of files;
  6. the check of the answers.
- **The version's configuration** — two sets of paths that do not overlap, so that no header depends on which of two rules Hosting applies:

## The deploy workflow

**R18. The deployment after a merge is done by `.github/workflows/deploy.yml` with four jobs: `target` decides what to deploy, with no access to anything; `config` applies the configuration as `infra-config` in the environment `production-config`; `api` deploys `api` as `api-deploy` in `production`; `app` releases the build as `hosting-publish` in `production-hosting`. The deployment goes only while `main` stands on the commit, and the list's parts count as changed against the commit of the last run that deployed — a push to `main`, green, and its job `Configuration` passed — not against the previous push. The tools are installed on the runner at exact versions and sha256 sums, and actionlint checks the workflow.** The author's decisions when planning T21, 2026-11-09, all four by the recommendations (RUN.md, T21). The model — `deploy.yml` of canvas-api, commit 0901af0; the sources — [architecture.md](architecture.md), section 4, read 2026-11-09.
- **Trigger** — a push to `main` on the paths of what the deployment deploys or what it does it with: `deploy/`, `tofu/` without the tests, `tools/deploy`, `tools/deploy-check`, `tools/ci`, the packages of `tools/`, the `justfile`, `.devcontainer/Dockerfile` — the tools are installed by its `ARG`s — the `spec` submodule — its `release-verify` — the workflow itself and its action. A run by hand, `workflow_dispatch`, applies the configuration and deploys the parts named: `image`, `api`, `facts`, `app`. One queue, `deploy`, without `cancel-in-progress`: a deployment once started is not cut off.
- **`target`** — `tools/deploy/target.mjs`:
  - `main` not on the commit — a green run with a notice: the commit that the branch stands on is deployed by its own run, and the old one would roll production back (R45 canvas-api);
  - no `tofu/ci.env`, `tofu/production.auto.tfvars` or `tofu/backend.hcl` — the project is not set up, a green run (T23);
  - no list — only the configuration;
  - otherwise the parts are the blocks `api` and `app` of `deploy/production.json` and `deploy/production/facts.json`, compared by meaning with the commit of the last run of `deploy.yml` that came from a push to `main`, passed, and in which the job `Configuration` passed, out of the last twenty green ones. A run that deployed nothing — `main` moved ahead, or the project is not set up — also ends green, and it does not count as the base.
