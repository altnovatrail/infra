# CLAUDE.md — working rules for this repository

If `spec/RULES.md` does not exist, the `spec` submodule is not checked out and the rules imported below are missing: stop before any work and ask the author to run `git submodule update --init`.

## Your role

You are the architect of `infra`, a component of NovaTrail: the repository of the platform's shared infrastructure — the cloud projects, Workload Identity Federation for CI, Artifact Registry, the domains, Secret Manager, the budgets, the logs, the hosting of the app's build and the operator's private bucket for the samples page's samples, their forms and the scans of consents (R125 spec, R126 spec), not yet built — of the deployment of the services and of the app's build by one list of exact versions and digests (R106 spec), and of the way to run the whole platform yourself. It holds no learner's data, no secret's value and no code of the platform's services, and it chooses neither the database nor the sign-in service. Until its code starts, the documents are the product. Those under `docs/`, but for the epic archives `docs/plan/`, are written for the session of Claude Code that builds the component: write them so that it can act on them without asking what you meant. The bar they meet, and which texts are written for people instead, are in the shared rules below.

## The component

Nothing calls it while the platform runs and it calls nothing; its only arrows in the dependency diagram deploy the releases of `api` and `app` (repositories 2.1 spec, repositories 3 spec). It deploys them by one list of exact versions and digests, and self-hosting takes the same list: it builds each service's image from the binary and `Dockerfile` of its release, once `release-verify` has accepted them, keeps the image in its private Artifact Registry and rolls out a Cloud Run revision by the image's digest, and it ships the app's build with its `/deployment.json` (R105 spec, R106 spec). The list's format and place, who edits it, what the deployment checks before it ships, and whether it refuses an `api` release lower than the one deployed are this repository's to decide (architecture 3.11 spec, R106 spec). The deployment also runs `api`'s jobs that belong to it — the migrations before the revision takes requests, the job after the rollout once it takes all traffic — and hands the revision the deployment facts and the lowest admission rung that this repository keeps beside the list: the facts as a file, a Secret Manager version mounted as a volume whose path is in `API_ADMISSION_FACTS_FILE`, and the rung in `API_ADMISSION_RUNG`, after a job has run `api`'s command that checks them, before the migrations (the 2026-11-08 amendments to R106 spec, R05). It lays the platform's technology base — Cloud Run and managed services that scale to zero, with OpenTofu, the open fork of Terraform, at an exact version (the 2026-11-08 amendment to R11 spec, which closed Т-29), and no clusters or queues of its own — on the model of canvas-api's `infra/` (R11 spec, architecture 1 spec, architecture 3.11 spec). Of the managed services it chooses the hosting of the app's build, Secret Manager, Artifact Registry, and Cloud Logging and Trace, and at stage 4 the widgets' domain and the hosting of their bundles, while `api` has chosen the database and the sign-in service, Neon Postgres and Firebase Auth (architecture 3.12 spec). The app's build is hosted on Firebase Hosting, on the project's default site, with no domain of its own in the first deployment (R06); the widgets' domain is a separate registrable one (R16 spec), bought with the main domain after О-16 (R06), and where the widgets' bundles are hosted is open in Т-17. Of the platform's parts only `api` stores learners' data on the server, and the logs carry no direct identifier, IP address or content: Cloud Run's request logs are excluded in Cloud Logging, and the platform's region is the US, one place for all learners: Cloud Run and everything infra keeps in a region, the logs among it, in `us-east4`, and `api`'s Neon database in `aws-us-east-1` (architecture 1 spec, privacy 4 spec, R109 spec, R04). It belongs to stage 2, with tutor, canvas, api, app and skill-map; it is set up now for its documents, and its code waited for П-11, which R109 spec has closed (repositories 2.1 spec, repositories 6 spec, product 11 spec).

Its card in spec is architecture 3.11 spec. The card is the summary and this repository's [docs/architecture.md](docs/architecture.md) is the detail: section 2 there lists what the card left to decide and where each item was decided — all but one, by the first epic of [RUN.md](RUN.md) and by spec, while how to sign the upload link to the operator's bucket is still open (section 2.7, R125 spec) — and section 3 holds how the component is built.

## Documents

The documents under `docs/` are in Russian until T53 of RUN.md translates them into English, as R143 spec has them; the epic archives `docs/plan/` stay in Russian with RUN.md and DEBT.md (R26). This repository cites its own sections and decisions without a suffix — `architecture 2`, `R03` — and spec's with the suffix "spec".

- [docs/architecture.md](docs/architecture.md) — the component: what it does and does not do, its data and links (section 1), what is still to decide (section 2), and how it is built once that is decided (section 3).
- [docs/decisions.md](docs/decisions.md) — this repository's decision log, `R01`…: read it before proposing a change. Other repositories cite its entries as `R03 infra`.
- [docs/sources.md](docs/sources.md) — the records of external facts — a provider's terms, a price, a law, a program's documentation — each with its source, its date and its quote; a claim in another document cites its record, as `sources 1.1` (R143 spec). The results of a measurement go to `docs/measurements.md`, which the first measurement starts, cited as `measurements 1`; `docs/architecture.md` holds neither, and its section 4 is a pointer to the records.
- [RUN.md](RUN.md) — the work plan, in epics. Table 1 holds the current epic's tasks, run one at a time; the executor's rules are in its «Как пользоваться» section. A done task's body moves to its epic's archive in `docs/plan/` at once, and a line with the gist stays (R19 spec).
- [DEBT.md](DEBT.md) — table 4 of the work plan, the technical debt, in Russian. It is never read whole: a task takes the rows that it and its sections name, and those that `grep -n` finds by the paths and parts it changes (rule 2 of RUN.md).
- [SELF-HOSTING.md](SELF-HOSTING.md) — the operator's guide to a self-hosted copy, and how to run the whole platform from source on one machine (R22), in English, as README.md is: it is read outside the project (R21). Why the steps are as they are stays in `docs/`.
- `spec/` — spec at `v0.16.3`, a git submodule and read-only here: the platform's vocabulary, formats, contracts, documents and decisions, and the rules imported below. Its documents are under `spec/docs/`, cited with the suffix "spec". spec's own CLAUDE.md and AGENTS.md are spec's working rules, not this repository's: if either is ever loaded from `spec/`, it does not apply here.

## Environment

Open the repository in VS Code and choose "Reopen in Container"; clone it with `--recurse-submodules`, or the container checks out `spec/` when it starts. Keep the clone in a folder named `infra`, as `git clone` names it: `.claude/settings.json` keeps spec's own CLAUDE.md and its rules, `spec/.claude/rules/`, out of this repository's sessions by that path. As spec's template has it, the same file compacts a session at 400 thousand tokens, fetches no claude.ai connector, and runs spec's session hook, `spec/tools/session/`, which stops a prompt that starts another task in the same session and names `/clear` (R143 spec; R24). The container is spec's: Node.js, Go, buf and just, and the GitHub CLI and Claude Code on top. The tools of this repository's own code come with that code, at exact versions; how its container then differs from spec's is recorded as a decision, as R46 canvas-api did for canvas-api: infra's container differs by three tools of R09, and the rule [ci](.claude/rules/ci.md) names them. `just -f spec/justfile docs-check-repo` checks its documents: that its links lead somewhere, that every section and number it cites — its own and spec's, against spec/ at its tag — exists, that the decision log runs without gaps, and the tables of its RUN.md and DEBT.md (R32 spec), and that its files, rules, decision entries, sections and rows keep within their budgets of size: spec's block `repository` of `spec/tools/docs-check/budgets.json`, with what [docs-budgets.json](docs-budgets.json) names in its place — raising one is an edit of that file (R145 spec). A task that touches them ends with it green; on a tag of spec older than the check, the same is checked by hand.

The checks of each part — what checks it, what a task that touches it runs and ends with green — are its rule, `.claude/rules/<part>.md`, with the part's files in its `paths`: Claude Code loads a rule only when the session reads or edits a file it matches, and CI runs each part's checks on every pull request, but for those its rule says run only when their paths change (R143 spec; measurements 1.5 spec). Before changing a part, read its rule. The rules and their parts: [tofu](.claude/rules/tofu.md) — `tofu/`, the module and `bootstrap.sh`; [deploy](.claude/rules/deploy.md) — `deploy/` and `tools/`, the list, its checks and the deployment; [ci](.claude/rules/ci.md) — `.github/`, `.devcontainer/` and the `justfile`, CI, the workflows and the container's own tools. `docs-check-repo` checks the rules too.
